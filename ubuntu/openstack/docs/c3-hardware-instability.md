# c3: kernel oops and segfaults after the reboot of 2026-10-22 (suspected CPU core)

## What happened
After a clean `systemctl reboot` (test of the new `/var/lib/nova` mount) c3 logged, within 2 minutes of idle running, **two kernel oopses** (`BUG: unable to handle page fault ... RIP: do_anonymous_page+0x39a`, process `openstack`, tainted after the second) and **two userland segfaults** in `python3.13` (`openstack` CLI), at 14:55:02, 14:55:46, 14:56:14 and 14:56:33. **All on CPU 8** (core 4, hyperthread pair CPU 8/9, P-core, max 6.0 GHz). No machine-check or EDAC messages. The earlier boot (2026-10-20 to 22, two days) and the one before it show **none**.
Side effect: the `openstack` CLI crashed in the middle of `c3-vms-start.sh`, which is why the first start attempts died silently (a second cause, found the same night: the script read from the ssh stdin; fixed with `</dev/null`).

## Hardware
MSI MAG Z790 TOMAHAWK MAX WIFI (BIOS A.B0, 2026-03-04), **Intel Core i9-14900K** (24 cores, 32 threads), microcode `0x133` (already past the 0x12B fix for the "Vmin shift" instability of 13th/14th gen CPUs, which cannot repair a core that was damaged before), 80 GB DDR5 from **two different kits**: one 32 GB Corsair `CMK32GX5M1B5200C40` and one 48 GB Crucial `CP48G56C46U5.C16B`, running at 4800 MT/s. Mixed-vendor, mixed-size DDR5 is a known source of instability too.

## What was done (reversible, not persistent)
`echo 0 > /sys/devices/system/cpu/cpu9/online; echo 0 > /sys/devices/system/cpu/cpu8/online`. Result: **145 consecutive `openstack` calls without a crash**, then the 17 VMs were started with `c3-vms-start.sh`, front doors 200, Patroni `db2` Leader / `db1` Sync Standby, 6 of 6 nodes Ready, 4 load balancers ONLINE (cka-api ERROR: cka is off). No kernel event since. Before the change, 4 events in 90 seconds, so this is strong evidence but not proof (the faults were sporadic).
**Persistent since the same night:** `/etc/systemd/system/c3-offline-cpus.service` (copy in `scripts/c3-offline-cpus.service`), a oneshot ordered before libvirt and nova-compute that writes 0 to `/sys/devices/system/cpu/cpu9/online` and `cpu8`, enabled. It has no `ExecStop` on purpose (stopping it, also at shutdown, must not bring the core back). **Verified:** unit enabled, `systemd-analyze verify` clean, started now with the cores already off (idempotent); **not yet verified at a real boot**: after the next reboot check `cat /sys/devices/system/cpu/offline` (expect `8-9`). To undo after the memtest/BIOS/RMA work: `systemctl disable --now c3-offline-cpus` and `echo 1 > /sys/devices/system/cpu/cpu8/online` (and `cpu9`), or reboot. Alternatives: BIOS (disable that core) or a kernel parameter.

## What to do (owner)
1. **Memory test:** boot memtest86+ (USB) for at least two full passes over the 80 GB (hours); a failure there says RAM, not CPU.
2. **BIOS:** update to the latest MSI BIOS for the Z790 (Intel microcode), load optimised defaults and **Intel Default Settings** (no "Multi-Core Enhancement"/"Enhanced Turbo", PL1/PL2 at Intel limits, no XMP/EXPO on the mixed kits). Keep memory at 4800 or lower.
3. If it persists on a specific core after both: **the CPU is degraded** (Intel extended the 13th/14th gen warranty to 5 years and replaces affected CPUs): RMA with Intel. Until then run with the core offline.
4. Treat the **runner VM kernel oops** seen earlier (2026-10-20) as possibly related: a faulting host core shows up in guests too.
5. Backups matter more while the host is suspect: the DR kit, the hourly Terraform-state snapshots and the Patroni pair are the protection; the nightly capture timer is still not installed.

## Also found: VMs do not come back after a clean reboot
`resume_guests_state_on_host_boot = true` only restarts VMs Nova still considers running. On a **clean** `systemctl reboot`, libvirt-guests shuts the guests down while nova-compute is still up, Nova notices the power-off and marks them stopped, and after the boot all 17 VMs stayed `SHUTOFF` (they came back by themselves in the 2026-10-20 tests only because those ended in a forced reset). Until that is solved, after a clean reboot run `scripts/c3-vms-start.sh` on c3 (stream it: `ssh c3 'bash -s' < scripts/c3-vms-start.sh`, or copy it). The new `/var/lib/nova` mount itself came up correctly before libvirt and nova (`var-lib-nova.mount`).

## Update 2026-10-22 evening: BIOS flashed, status unclear (read this first)
- **BIOS 7E25vAB (`A.B0`) -> 7E25vAC (`A.C0`, 2026-08-25, "improved memory compatibility", ME 16.1.42.2872)**, flashed by the owner. Microcode `0x133` -> **`0x137`**. Memory still 4800 MT/s.
- **Evidence of the fault:** 4 faults on CPU 8 before the mitigation (14:55 to 14:56); with the core back online and `memtester`/`stress-ng` running, 2 more python segfaults on CPU 8 (15:57 and 16:02) although `stress-ng` and `memtester` themselves reported no failure. **First boot after the BIOS flash (16:13): two kernel oopses within 20 seconds, on CPU 8 and then CPU 9** (same physical core; `uwsgi_python3` and `apache2`; `alloc_pages_bulk_array_mempolicy` and `do_anonymous_page`). That boot was probably still on the defaults the flash restores; the owner then re-set the BIOS options.
- With CPUs 8-9 **offline** (unit `c3-offline-cpus` enabled), the python load test ran clean (30 threads, 4 min, 0 mismatches, 0 events).
- **Then the owner rebooted with all 32 threads online and the unit disabled (BIOS settings re-applied):** at the time of writing, **14+ minutes, 0 kernel events, 17 VMs running, all checks green** (front doors 200, Patroni `db1` Leader / `db2` Sync Standby timeline 31, etcd 3/3, 6/6 nodes Ready, load balancers ONLINE, cka off). This is **encouraging but not proof**: the earlier faults came in bursts, with quiet stretches of an hour or more between them. Possible reading: the BIOS settings (not the flash) or the new microcode changed something; or the core fails intermittently.
- **Decision rule until it is understood:** keep all cores online only while the kernel log is watched. At the first `Oops`/`segfault` on CPU 8/9, run `systemctl enable --now c3-offline-cpus` (offlines both at once and at every boot). Cheap check: `journalctl -k -b | grep -E "Oops|segfault|BUG:|Machine check"` once or twice a day for a week. If anything shows: offline the core and file the Intel RMA (i9-14900K, 5-year extended warranty for 13th/14th gen).
- Unrelated noise: `ath12k_pci ... failed to enqueue rx buf: -28` is the board's Wi-Fi 7 card (unused, interface DOWN); harmless. Can be blacklisted (`/etc/modprobe.d`) or disabled in the BIOS.
- Leftover pod objects after the shutdowns (`Error`/`ContainerStatusUnknown`, message "terminated in response to imminent node shutdown") were deleted with `kubectl delete pod -A --field-selector=status.phase=Failed`; the kubelet's graceful shutdown leaves such records after each c3 stop.

- **2026-10-22 late: kernel 6.12.113 installed** (running 6.12.95 until the next reboot; old kernels kept as fallback). From the next boot on, two things differ from the faulting boots (BIOS `A.C0` and the new kernel): when reading results, note which kernel (`uname -r`) was running.
